# 00. 전체 진행 계획

이 문서는 **Qodo와 CodeRabbit을 어떤 순서로 시험했고 앞으로 무엇을 할지 보여주는 계획표**야.

## 목표

우리가 알고 싶은 것은 기능 개수가 아니야.

```text
실제 버그를 잘 찾는가?
정상 코드를 버그라고 잘못 말하지 않는가?
수정 코드가 진짜 문제를 해결하는가?
둘 다 반복해서 놓치는 문제가 있는가?
```

마지막 질문에서 반복되는 문제가 나오면 그 부분을 MUOT의 기능으로 만들 거야.

## 전체 순서

```text
1. Flask의 실제 과거 버그 선택
↓
2. 현재 코드에 같은 원리의 버그를 다시 넣음
↓
3. 버그가 없는 정상 코드도 준비
↓
4. 각 시험마다 Qodo용·CodeRabbit용 PR을 따로 만듦
↓
5. 두 제품에 똑같은 코드를 리뷰시킴
↓
6. 댓글과 수정 코드를 저장
↓
7. 제품에 안 보여준 정답 테스트로 확인
↓
8. 둘 다 놓친 문제를 다른 모양으로 다시 시험
↓
9. 반복해서 확인된 빈틈을 MUOT 기능으로 만듦
```

## 완료한 작업

| 작업 | 상태 |
|---|---|
| Flask 코드와 Git 기록 가져오기 | 완료 |
| 닫힌 이슈와 PR 자료 가져오기 | 완료 |
| 버그 시험 P01~P04 만들기 | 완료 |
| 정상 코드 시험 C01~C02 만들기 | 완료 |
| 제품별 PR 12개 만들기 | 완료 |
| Qodo 리뷰 6개 실행 | 완료 |
| CodeRabbit 리뷰 6개 실행 | 완료 |
| 댓글과 코드 수정안 확인 | 완료 |
| 쉬운 결과 문서 작성 | 완료 |

## 아직 할 작업

| 작업 | 이유 |
|---|---|
| P02의 두 문제를 각각 따로 시험 | 한 PR에 문제가 두 개 섞였기 때문 |
| P04의 추가 문제를 따로 시험 | CodeRabbit도 같은 조건에서 보게 하기 위해 |
| 다른 사람이 제품 이름을 가리고 채점 | 우리가 원하는 쪽으로 점수를 주는 일을 막기 위해 |
| 같은 문제를 다른 코드 모양으로 반복 | 한 번 우연히 맞힌 것인지 확인하기 위해 |

## 시험 문제를 고르는 기준

다음 조건을 모두 만족해야 해.

- Flask에서 실제로 발생한 버그인가?
- 실제 수정 PR이나 테스트가 남아 있는가?
- 현재 Flask 코드에 다시 넣을 수 있는가?
- 제품이 단순 검색이 아니라 코드를 이해해야 찾을 수 있는가?
- 위험한 공격을 실제로 실행하지 않고도 확인할 수 있는가?

## 한 PR에는 문제 하나만 넣는다

원칙은 간단해.

```text
PR 하나
+= 찾아야 할 버그 하나
```

문제가 여러 개 섞이면 제품이 하나만 찾았을 때 점수를 정하기 어려워져.

이번 P02와 P04에서는 나중에 다른 문제가 함께 생긴 것을 발견했어. 이 사실을 숨기지 않고, 해당 시험은 깨끗한 비교 점수에서 따로 뺐어.

## 왜 제품별 PR을 따로 썼나

한 PR에 두 제품을 함께 부르면 먼저 남긴 댓글을 다른 제품이 볼 수 있어.

그래서 이렇게 나눴어.

```text
같은 코드 변경
├── Qodo만 리뷰하는 PR
└── CodeRabbit만 리뷰하는 PR
```

PR 번호는 다르지만 각 쌍의 코드는 같아.

## 무엇을 기록했나

읽는 문서에는 필요한 것만 남겼어.

- 어떤 버그였는가
- 제품이 찾았는가
- 정상 코드에 잘못 경고했는가
- 수정 코드를 줬는가
- 그 수정 코드가 테스트를 통과했는가
- 실제 댓글과 원본 버그 링크

실행 시각, 내부 실행 번호, 긴 코드 번호는 GitHub 원문과 Git 기록에 남아 있어서 읽는 문서에서는 뺐어.

## 결과를 판단하는 방법

| 결과 | 뜻 |
|---|---|
| 제대로 찾음 | 원인·문제가 생기는 조건·사용자 결과를 모두 맞힘 |
| 일부만 찾음 | 방향은 맞지만 중요한 설명이 빠짐 |
| 못 찾음 | 실제 버그를 말하지 않음 |
| 잘못된 경고 | 정상 코드를 버그라고 말함 |

## 수정 코드 확인 방법

```text
제품이 코드 수정안 제공
↓
우리가 별도 코드에 적용
↓
제품에 안 보여준 정답 테스트 실행
↓
기존 테스트 전체 실행
↓
완전히 고침 / 일부만 고침 / 못 고침으로 기록
```

## 1차 결과

```text
P01, P03, P04
→ 두 제품 모두 찾음

P02
→ 두 제품 모두 핵심 문제를 못 찾음
→ 같은 코드에 섞인 다른 문제는 둘 다 찾음

C01, C02
→ 두 제품 모두 잘못된 경고 없음
```

## 다음 실험이 끝나야 말할 수 있는 것

지금은 시험이 적어서 최종 승자를 고를 수 없어.

P02를 나눠 다시 시험하고, 같은 종류의 버그를 다른 코드 모양에서도 반복해야 다음을 말할 수 있어.

- 어떤 제품이 더 안정적으로 버그를 찾는가
- 어떤 제품이 정상 코드에 덜 시비를 거는가
- 어떤 제품의 수정 코드가 더 완전한가
- MUOT가 어떤 빈틈을 먼저 막아야 하는가

딱 기억해.

**지금은 1차 방향을 찾은 단계이고, 반복해서 같은 결과가 나와야 진짜 장단점으로 확정할 수 있어.**
