# 00. 전체 진행 계획

이 문서는 **Qodo와 CodeRabbit을 같은 시험지와 같은 판정표로 비교하는 전체 작업 순서**야.

## 원래 뭐가 문제였나

기능표만 만들면 이런 결론이 나와.

```text
Qodo도 자동 리뷰 가능
CodeRabbit도 자동 리뷰 가능
↓
둘 다 비슷해 보임
```

근데 실제 팀이 돈을 내는 이유는 기능 이름 때문이 아니야. 사람이 놓칠 버그를 찾아주고, 불필요한 댓글을 줄여주기 때문이야.

그래서 이번 비교는 설명 페이지가 아니라 **실제 Flask 버그 PR**을 기준으로 진행해.

## 최종 목표

다음 세 질문에 증거로 답하면 실험이 끝나.

1. 어떤 종류의 실제 버그를 각 제품이 정확히 찾는가?
2. 어떤 종류의 정상 변경에 잘못된 경고를 남기는가?
3. 두 제품이 반복해서 놓치는 문제를 어떤 기능으로 보완할 것인가?

## 완료 조건

- 두 제품이 같은 결함·정상 케이스를 리뷰했다.
- 제품별 원문 댓글과 최초 응답 시간이 저장됐다.
- 제품 이름을 가린 상태로 판정했다.
- 수정 제안은 숨은 테스트와 전체 테스트로 실행 검증했다.
- 공통 실패를 최소 두 개 이상의 변형 케이스에서 다시 확인했다.
- 검증된 공통 실패만 `06-우리가-만들어야할-기능.md`의 요구사항으로 승격했다.

## 전체 흐름

```text
0. 실험 규칙 고정
↓
1. 원본 버그 선정
↓
2. 결함 PR과 정상 대조군 제작
↓
3. 제품 설치 조건 기록
↓
4. 제품별 쌍둥이 PR에서 리뷰 실행
↓
5. 원문 수집과 제품명 가리기
↓
6. 숨은 테스트로 판정
↓
7. 공통 허점 재시험
↓
8. 제품 명세 확정
```

## 0단계: 규칙을 먼저 잠근다

결과를 본 뒤 기준을 바꾸면 원하는 제품이 이기게 만들 수 있어.

실행 전에 아래 값을 커밋으로 고정한다.

- 정확히 탐지·부분 탐지·놓침·오탐의 뜻
- 케이스 목록과 결함/정상 구분
- 숨은 테스트의 예상 결과
- 제품별 실행 횟수
- 시간 측정 시작점과 종료점
- 수정 제안 검증 명령

관련 문서: [평가와 판정 기준](03-평가와-판정기준.md)

## 1단계: 원본 문제를 고른다

원본 자료는 `benchmark/`에서 찾는다.

채택 조건은 다섯 개야.

- 실제 이슈나 PR에 사용자 문제가 기록되어 있다.
- 수정 코드 또는 회귀 테스트로 정답을 확인할 수 있다.
- 최신 Flask 코드에 자연스럽게 다시 만들 수 있다.
- 단순 문법 오류가 아니라 실행 흐름을 이해해야 찾을 수 있다.
- 위험한 공격이나 외부 서비스 비용 없이 재현할 수 있다.

채택하지 않는 문제:

- 오탈자와 포매팅만 바뀐 문제
- 환경을 현실적으로 재현할 수 없는 문제
- 정답이 사람 취향에 따라 달라지는 리팩터링
- 현재 코드에 옮기면서 원래 원인이 사라지는 문제

## 2단계: 시험 PR을 만든다

한 PR에는 판정할 핵심 문제를 하나만 넣는다.

```text
benchmark-base
↓
결함 원리 하나를 현재 코드에 이식
↓
공개 테스트 통과 확인
↓
숨은 테스트 실패 확인
↓
중립적인 제목으로 draft PR 생성
```

정상 대조군도 만든다.

정상 대조군은 동작을 깨지 않고 코드 모양만 비슷하게 바꾼 PR이야. 제품이 여기에 존재하지 않는 장애를 경고하면 오탐으로 기록한다.

현재 실행한 표본:

- CodeRabbit용: #6, #7, #8, #9, #10, #11
- Qodo용 쌍둥이: #6174, #6175, #6176, #6177, #6178, #6179
- 두 제품 PR의 base SHA와 head SHA가 케이스별로 같음
- 리뷰 실행 완료: 2026-09-03

## 3단계: 제품 조건을 맞춘다

두 제품에 다음 조건을 똑같이 준다.

| 조건 | 기록할 값 |
|---|---|
| 저장소 접근 | 읽을 수 있는 저장소와 파일 범위 |
| 실행 모드 | 자동 또는 수동 |
| 설정 | 기본 설정 파일 전체와 SHA |
| 버전 | 제품·앱·에이전트 버전 |
| 요금제 | 실제 사용한 플랜 |
| 추가 지시 | 제품에 전달한 문장 원문 |
| 실행 시각 | UTC 시작·완료 시각 |

기본 비교는 추가 지시가 없는 상태로 한다. 설정을 튜닝한 비교는 별도 라운드로 분리한다.

## 4단계: 제품별 쌍둥이 PR을 쓴다

한 PR에서 두 제품을 같이 실행하면 먼저 남긴 댓글이 뒤 제품의 문맥에 들어갈 수 있어.

그래서 실제 비교는 이렇게 한다.

```text
같은 base commit + 같은 diff
↓
Qodo 전용 PR 생성

같은 base commit + 같은 diff
↓
CodeRabbit 전용 PR 생성
```

두 PR은 제목, 본문, diff, 공개 테스트 결과가 같아야 한다. 브랜치 이름과 PR 번호만 달라도 된다.

기존 #6~#11은 CodeRabbit 전용으로 사용했고, 같은 commit을 가리키는 #6174~#6179를 Qodo 전용으로 만들었어.

자동 리뷰는 다음 파일로 껐어.

```text
.coderabbit.yaml
= CodeRabbit 자동 리뷰 끔

.pr_agent.toml
= Qodo 자동 명령 목록을 비움
```

그다음 CodeRabbit PR에는 `@coderabbitai full review`, Qodo PR에는 `/agentic_review`만 남겼어.

## 5단계: 원문을 저장한다

리뷰가 끝나면 즉시 다음 자료를 제품별 결과 문서에 기록한다.

- PR URL과 commit SHA
- 리뷰 시작·완료 시각
- 요약 댓글 원문
- 인라인 댓글 원문과 파일·라인
- 심각도와 수정 제안
- 체크 실행 결과
- 재실행 여부와 이유

원문을 요약해서 저장하면 나중에 판정자가 제품의 실제 표현을 확인할 수 없어. 반드시 링크와 원문을 같이 남긴다.

## 6단계: 제품 이름을 가리고 판정한다

판정자는 `Qodo`, `CodeRabbit`이라는 이름 대신 `제품 A`, `제품 B`만 본다.

각 댓글은 다음 순서로 확인한다.

```text
실제 코드 위치를 짚었나?
↓
원인을 설명했나?
↓
발생 조건을 설명했나?
↓
사용자 결과를 설명했나?
↓
수정 제안이 테스트를 통과하나?
```

판정 규칙은 [03-평가와-판정기준.md](03-평가와-판정기준.md)를 따른다.

## 7단계: 공통 허점을 다시 시험한다

두 제품이 한 번 같이 놓쳤다고 바로 우리 기능으로 만들면 안 돼. 우연일 수 있기 때문이야.

```text
공통 놓침 발견
↓
같은 원리, 다른 코드 모양으로 변형
↓
제품별로 다시 리뷰
↓
두 제품이 반복해서 놓침
↓
검증된 공통 허점으로 등록
```

검증 결과는 [05-두제품이-놓친-문제.md](../05-두제품이-놓친-문제.md)에 기록한다.

## 8단계: 기능으로 바꾼다

공통 허점 하나는 기능 요구사항 하나로 바로 연결돼야 해.

예시:

```text
두 제품이 실행 순서 버그를 반복해서 놓침
↓
과거 회귀 테스트에서 호출 순서 불변식 추출
↓
새 PR에서 순서가 바뀌면 숨은 시나리오 실행
↓
실행 증거와 함께 경고
```

기능 초안은 [06-우리가-만들어야할-기능.md](../06-우리가-만들어야할-기능.md)에 있다.

## 1차 실행에서 바로 드러난 것

```text
P01, P03, P04의 주 결함
→ 두 제품 모두 탐지

P02의 숨은 주 결함
→ 두 제품 모두 놓침
→ 대신 둘 다 같은 부수 결함을 탐지

정상 C01, C02
→ 두 제품 모두 오탐 없음
```

단, P02와 P04에는 서로 다른 실패 조건이 둘 이상 들어 있다는 사실이 리뷰 후 확인됐어. 따라서 원래 정답 기준 점수와 `단일 결함 원칙을 통과한 점수`를 나눠서 공개한다.

딱 기억해.

**실험은 PR을 여는 일이 아니라, 같은 조건과 고정된 판정표로 결과를 다시 확인할 수 있게 만드는 일이야.**
