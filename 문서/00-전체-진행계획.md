# 00. Qodo·CodeRabbit 본시험 전체 계획

이 문서는 **무엇을 왜 확인하는지부터, 언제 시험을 끝냈다고 말할 수 있는지까지** 한 번에 보여주는 기준표야.

P01~P04와 C01~C02는 이미 끝난 작은 예비시험이야. 방향을 잡는 자료로만 쓰고, 앞으로 계산할 본시험 점수에는 넣지 않아.

## 1. 현재 저장소 — 기존 자료를 버리지 않고 다시 쓰려고

지금 저장소는 **자료 보관과 이번 내부 비교 실행**에 함께 쓴다.

- 다시 쓸 것: Flask 코드, 과거 이슈와 PR, 예비시험 댓글, 실행 기록
- 그대로 둘 것: 기존 브랜치, PR, 이슈, 문서
- 본시험에 넣지 않을 것: P01~P04와 C01~C02의 점수

## 2. 정확한 비교 대상 — Flask와 두 제품의 역할을 헷갈리지 않으려고

- Flask는 시험 문제의 재료를 주는 오픈소스야.
- Qodo와 CodeRabbit은 시험을 보는 제품이야.
- 우리가 비교하는 것은 Flask가 아니라 **두 제품의 리뷰 능력**이야.

## 3. 현재 저장소에서 실행할 때의 한계 — 정답 단서가 있다는 사실을 숨기지 않으려고

이 저장소에는 정답이 너무 많이 보여.

- 과거 수정 내용이 있는 `CHANGES.rst`와 `docs/changes.rst`
- 정답 테스트가 공개된 `benchmark/oracles/`
- Flask의 과거 PR과 이슈 자료가 있는 `benchmark/`
- 정답을 설명하는 실험 문서와 PR 이름
- 수정 전후 내용이 모두 남은 Git 기록과 수천 개의 참조 이름

따라서 이번 실행 결과는 완전한 블라인드 시험이 아니라 **내부 비교**로 표시한다.

## 4. 실행 저장소 구성 — 같은 저장소에서 두 제품의 리뷰를 나누려고

별도 저장소는 만들지 않고 현재 저장소에서 쌍둥이 PR 두 개를 만든다.

```text
같은 기준 코드와 같은 변경 커밋
├── 첫 PR: Qodo 명령만 실행
└── 둘째 PR: CodeRabbit 명령만 실행
```

저장소 이름과 PR 제목에는 제품 이름, 시험, 버그, 정답, 문제 번호를 넣지 않는다.

## 5. 쌍둥이 PR의 정확한 뜻 — 두 제품이 같은 코드를 봤다고 증명하려고

쌍둥이 PR은 PR 번호만 다르고 내용은 같아야 해.

- 시작 코드
- 바뀐 파일과 코드
- 커밋
- PR 제목과 설명
- 제품에 보이는 테스트

두 PR의 시작 코드 번호, 변경 코드 번호, 파일 수, 바뀐 줄 수, 변경 내용 지문을 저장한다. 하나라도 다르면 그 쌍은 점수에서 뺀다.

## 6. 시험 문제를 만드는 방법 — 억지로 만든 쉬운 버그를 피하려고

실제 Flask 이슈와 합쳐진 수정 PR에서 문제를 고른다.

```text
실제 문제 확인
↓
왜 생겼는지 확인
↓
정답 테스트 확인
↓
현재 코드에 자연스러운 작업으로 다시 구성
↓
PR 하나에 버그 하나만 넣기
```

제품에는 원본 이슈 번호와 정답 테스트를 보여주지 않는다.

## 7. 사용할 오픈소스 범위 — 결과가 어디까지 맞는 말인지 분명히 하려고

첫 본시험은 Flask와 Python만 다룬다. 따라서 결과도 “Flask 기반 시험에서는”이라고 말한다.

나중에 범위를 넓히려면 JavaScript의 Express와 Go의 chi처럼 언어와 구조가 다른 프로젝트에서 별도 시험을 한다.

## 8. 이번 문제 수 — 사용자가 정한 범위를 넘기지 않으려고

- 실제 결함 4개
- 정상 코드 2개
- 문제마다 쌍둥이 PR 2개
- 전체 12개 PR
- 128개·208개 확장 계획은 진행하지 않음

## 9. PR 크기 구성 — 실제 업무처럼 작은 변경과 큰 변경을 함께 보려고

이번 6문제는 실제 Flask 수정 범위 그대로 사용한다. 줄 수를 맞추기 위한 의미 없는 코드는 넣지 않는다.

## 10. 반드시 포함할 문제 종류 — 한 종류만 잘 잡는 제품을 전체적으로 좋다고 착각하지 않으려고

입력값, 주소와 포트, 대소문자, 글자 변환, 세션과 쿠키, 보안 설정, 오류 처리, 정리 작업 순서, 신호와 함수 호출 순서, 스트리밍 종료, URL 연결, 이동 응답, HTML 안전 처리, 기본값, 명령줄, 예전 사용법 호환, 여러 파일 연결 문제를 골고루 넣는다.

단순 오타, 빠진 import, 자동 정리 도구가 바로 고치는 문제는 넣지 않는다.

## 11. 난이도 구분 — 쉬운 문제와 어려운 문제에서 실력이 어떻게 달라지는지 보려고

제품 실행 전에 난이도를 정한다.

- 쉬움: 바뀐 코드 근처만 읽어도 찾을 수 있음
- 중간: 같은 파일의 다른 함수나 상태를 따라가야 함
- 어려움: 여러 파일, 실행 순서, 예외 뒤 동작까지 따라가야 함

제품 결과를 본 뒤 난이도를 바꾸지 않는다.

## 12. 정상 대조군 — 정상 코드에도 마구 경고하는지 보려고

버그가 없는 현실적인 변경 2개도 함께 넣는다.

예를 들면 내부 코드 정리, 속도 개선, 입력 확인 강화, 테스트 정리야. 정상 코드에 실제로 없는 문제를 있다고 말하면 잘못된 경고로 기록한다.

## 13. 정답과 숨은 테스트 보관 — 제품이 정답을 미리 읽지 못하게 하려고

정답과 제품에 보여주지 않을 테스트는 다음 로컬 폴더에 둔다.

`/Users/seonho/Documents/Codex/2026-09-03/new-chat/private-oracle`

이 폴더는 Git 저장소 밖에 둔다. 정답 테스트는 다음 세 가지를 만족해야 한다.

1. 정상 코드에서는 통과
2. 버그가 든 코드에서는 실패
3. 올바르게 고친 코드에서는 다시 통과

## 14. 정답 단서 검사 — 문서나 Git 기록에서 답을 찾지 못하게 하려고

PR을 열기 전에 실행 저장소 전체를 검사한다.

- 원본 이슈와 PR 번호
- 정답을 말하는 변경 기록
- `bug`, `fix`, `defect`, `oracle`, `benchmark` 같은 이름
- P01 같은 시험 번호
- 정답이 드러나는 테스트 이름과 설명
- 미래의 수정 커밋과 불필요한 Git 기록

단서가 하나라도 남으면 PR을 열지 않는다.

## 15. 제품 실행 조건 — 한 제품만 유리한 조건을 받지 않게 하려고

먼저 두 제품의 기본 설정으로 비교한다. 두 제품이 읽을 수 있는 코드, 테스트, 검색 범위와 댓글 권한을 같게 맞춘다.

제품이 테스트를 실행했다는 화면이나 기록이 없으면 “테스트까지 했다”고 쓰지 않는다.

## 16. 실행 순서 — 시간대와 먼저 달린 제품의 영향을 줄이려고

문제마다 먼저 실행할 제품을 번갈아 바꾼다.

```text
1번 문제: Qodo 먼저
2번 문제: CodeRabbit 먼저
3번 문제: Qodo 먼저
```

두 제품이 끝나기 전에는 사람이 댓글, 정답, 수정 코드를 추가하지 않는다.

## 17. 저장할 원본 자료 — 기억이나 감상 대신 증거로 판단하려고

GitHub CLI와 API로 다음 원본을 JSON으로 저장한다.

- PR 내용과 변경 코드
- 제품 리뷰와 댓글
- 검사 실행 결과
- 시작 코드와 변경 코드 번호
- 리뷰 요청, 첫 유효 지적, 리뷰 완료 시각
- 제품 설정과 확인 가능한 실행 정보

화면 사진은 보기 편한 보조 자료로만 쓰고, 원본은 JSON으로 남긴다.

## 18. 무엇을 잡았다고 인정할지 — 애매한 일반론을 정답으로 세지 않으려고

- 정확히 찾음: 위치, 원인, 생기는 조건, 사용자 결과를 모두 설명
- 일부 찾음: 방향은 맞지만 중요한 설명이 빠짐
- 못 찾음: 주 문제를 말하지 않음
- 잘못된 경고: 정상 코드에 없는 문제를 있다고 말함
- 스타일 의견: 이름과 표현 취향이며 버그 점수와 따로 기록

같은 말을 여러 댓글로 반복해도 한 건으로 센다.

## 19. 수정 제안 확인 — 그럴듯한 코드가 진짜 고치는지 보려고

제품이 실제로 적용할 수 있는 수정 코드를 줬을 때만 확인한다.

```text
제품 수정 코드를 별도 작업 공간에 적용
↓
기존 공개 테스트 실행
↓
제품에 안 보여준 정답 테스트 실행
↓
새로 깨진 기능이 있는지 확인
```

완전히 고침, 일부만 고침, 적용 실패, 다른 기능을 깨뜨림, 수정 코드 없음으로 기록한다.

## 20. 반복 안정성 시험 — 한 번 우연히 맞힌 것인지 구분하려고

이번 12개 PR 범위에는 반복시험을 추가하지 않는다. 반복시험은 사용자가 별도로 요청할 때만 진행한다.

## 21. 측정할 숫자 — 댓글 수가 아니라 실제 성능을 비교하려고

주요 숫자는 다음과 같아.

- 정확히 찾은 비율과 일부까지 찾은 비율
- 정상 코드에 잘못 경고한 비율
- 원인, 생기는 조건, 사용자 결과를 맞힌 비율
- 적용할 수정 코드를 준 비율
- 수정 코드가 정답 테스트를 통과한 비율
- 처음 맞는 지적과 전체 리뷰가 끝날 때까지 걸린 시간
- 반복해서 같은 결과를 낸 비율
- 제품 자체가 실행되지 않은 비율

항상 “몇 개 중 몇 개”를 함께 쓰고, 가운데 값과 95% 신뢰구간도 표시한다.

## 22. 공정성을 깨뜨리는 상황 — 실험 실패를 제품 실패로 세지 않으려고

GitHub 장애, 제품 미실행, 사용량 제한, 권한 차이, 쌍둥이 코드 불일치, 정답 노출, 사람의 답 댓글, 상대 제품 댓글 노출, 흔들리는 정답 테스트가 생기면 정상 점수에서 뺀다.

무엇이 깨졌는지와 다시 실행했는지를 따로 기록한다.

## 23. MUOT 기능 선정 — 한 번 나온 특이한 실패로 제품을 만들지 않으려고

다음 조건을 모두 만족해야 MUOT 기능 후보가 된다.

- 서로 다른 사례가 5개 이상
- Qodo와 CodeRabbit이 각각 절반 이상 놓침
- 서로 다른 코드 영역 두 곳 이상에서 나타남
- 제품이 안 돌아서 놓친 사례가 아님
- 정답 단서가 없는 곳에서도 반복됨
- 정상 코드에 같은 규칙을 적용해도 잘못된 경고가 심하지 않음

후보 기능은 사용한 사례와 마지막 확인용 사례를 나눠 다시 검증한다.

## 25. 진행 보고 방식 — PR 수가 아니라 제대로 된 진행인지 확인하려고

매 단계가 끝날 때 다음만 짧게 보고한다.

- 끝낸 문제 수
- 만든 PR 수
- 정상 실행 수
- 뺀 사례 수와 이유
- 다음 작업
- 사용자가 정해야 할 것

## 26. 외부 작업 안전 규칙 — 대량 작업 중 기존 자료를 망가뜨리지 않으려고

GitHub 작업은 브라우저 수작업보다 CLI와 API를 먼저 쓴다. 기존 브랜치, PR, 이슈, 문서를 지우거나 강제로 덮어쓰지 않는다.

대량 PR을 만들기 전에는 준비 결과와 저장소 수, 설치할 GitHub App, 예상 PR 수, 비용, 시간, 공개 여부, 정답 단서 검사 결과를 사용자에게 보여주고 확인받는다.

## 27. 중단 조건 — 잘못된 시험을 계속 늘리지 않으려고

정답 단서, 쌍둥이 코드 불일치, 권한 차이, 흔들리는 정답 테스트, 재현되지 않는 버그, 반복되는 제품 미실행, 사용량이나 요금 제한이 발견되면 새 PR 생성을 멈추고 원인부터 고친다.

## 28. 완료 조건 — 일부만 끝내고 전체가 끝났다고 착각하지 않으려고

버그 4개와 정상 코드 2개, 쌍둥이 PR 12개, 정답 확인, 원본 JSON, 판정 문서까지 저장하면 이번 실행은 완료야.

## 29. 최종 보고서의 결론 범위 — Flask 결과를 모든 코드에 맞는 말처럼 과장하지 않으려고

“이번 Flask 결함 4개 중 몇 개를 찾았다”처럼 실제 자료의 범위 안에서만 말한다.

“항상 더 좋다”, “모든 프로젝트에서 더 정확하다”, “MUOT가 두 제품보다 뛰어나다”처럼 시험하지 않은 내용은 말하지 않는다.

## 30. 가장 먼저 할 일 — 준비 없이 대량 PR부터 만들지 않으려고
