# 01. Flask를 시험 대상으로 고른 이유

이 문서는 **왜 수많은 오픈소스 중 Flask를 Qodo·CodeRabbit 시험 대상으로 골랐는지 설명하는 문서**야.

## 한 줄 결론

Flask는 코드가 비교적 작고 읽기 쉬우면서도, 실제 사용자 버그와 수정 기록이 충분히 남아 있어 시험 문제를 만들기 좋아.

## 우리가 필요했던 조건

시험 대상은 다음 조건을 만족해야 했어.

- 실제 사용자가 많이 쓰는 프로젝트
- 과거 이슈와 수정 PR이 충분한 프로젝트
- 버그를 고친 테스트가 남아 있는 프로젝트
- 전체 테스트를 현실적인 시간 안에 실행할 수 있는 프로젝트
- 코드를 이해하지 않고 단순 검색만 해서는 찾기 어려운 문제가 있는 프로젝트
- 라이선스와 공개 범위가 분명한 프로젝트

Flask는 이 조건에 잘 맞았어.

## 실제 버그 기록이 많다

Flask에는 사용자가 신고한 이슈, 수정 PR, 리뷰 댓글, 릴리스 기록이 공개돼 있어.

그래서 우리가 상상으로 버그를 만들 필요가 없어.

```text
실제 사용자 문제
↓
Flask 개발자의 수정 PR
↓
문제를 확인하는 테스트
↓
우리의 시험 문제
```

## 코드 크기가 알맞다

너무 작은 프로젝트는 현실적인 버그가 부족할 수 있어.

반대로 아주 큰 프로젝트는 테스트 한 번에 오래 걸리고, 버그 하나를 이해하는 데 필요한 코드가 너무 많아져.

Flask는 웹 서버의 실제 동작을 다루지만 전체 구조는 비교적 따라가기 쉬워. 첫 실험 대상으로 알맞아.

## 평범한 테스트와 특별한 정답 테스트를 나눌 수 있다

리뷰 제품은 기존 테스트를 볼 수 있어.

하지만 우리가 버그를 확인하려고 따로 만든 결정적인 입력은 리뷰가 끝날 때까지 보여주지 않았어.

예를 들면 P01은 이래.

```text
평범한 서버 주소
→ 기존 테스트 통과

IPv6 서버 주소
→ 제품에 안 보여준 정답 테스트에서 버그 발생
```

이렇게 해야 제품이 테스트 답을 읽은 것이 아니라 코드를 보고 문제를 찾았는지 확인할 수 있어.

## 전체 테스트를 실행할 수 있다

이번 환경에서 Flask의 기존 테스트 493개를 모두 실행할 수 있었어.

그래서 제품이 준 수정 코드가 한 문제만 고치고 다른 기능을 망가뜨리지는 않았는지 확인할 수 있었어.

## 다양한 종류의 버그가 있다

이번에는 다음 문제를 골랐어.

| 시험 | 문제 종류 |
|---|---|
| P01 | IPv6 서버 주소 처리 |
| P02 | 프로그램 종료 순서 |
| P03 | 사용자가 직접 지정한 설정의 우선순위 |
| P04 | HTML 파일 이름과 안전 처리 |

주소 처리, 종료 순서, 설정, 보안 관련 동작을 한 저장소에서 시험할 수 있었어.

## Flask라고 해서 완벽한 대상은 아니다

Flask 하나에서 얻은 결과를 모든 언어와 프로젝트에 그대로 적용할 수는 없어.

- Python 코드만 시험했어.
- 웹 프레임워크 문제만 시험했어.
- 아주 큰 여러 저장소 구조는 시험하지 않았어.
- 성능이 중요한 시스템 코드는 시험하지 않았어.

따라서 다음 단계에서는 다른 Python 프로젝트나 다른 언어 프로젝트도 추가해야 해.

## 문제를 고를 때 제외한 것

다음 문제는 사용하지 않았어.

- 글자 수정이나 문서 수정처럼 코드 이해가 필요 없는 것
- 정답이 사람 취향에 따라 달라지는 코드 정리
- 현재 코드에서 안전하게 다시 만들기 어려운 문제
- 실제 공격을 실행해야만 확인할 수 있는 문제
- 하나의 PR에 서로 다른 문제가 너무 많이 섞이는 변경

딱 기억해.

**Flask는 실제 버그 기록이 많고 테스트가 빠르며 코드도 따라가기 쉬워 첫 비교 대상으로 골랐어.**
