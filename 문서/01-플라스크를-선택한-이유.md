# 01. Flask를 선택한 이유

Flask는 **실제 버그 기록, 수정 PR, 테스트, Git 이력이 한곳에 있어 리뷰 제품의 실력을 다시 시험하기 좋은 Python 프로젝트**야.

## 원래 어떤 대상을 찾았나

처음에는 유명한 오픈소스면 아무거나 쓸 수 있어 보여.

근데 유명하기만 해서는 부족해.

```text
이슈는 많은데 정답 PR이 없음
↓
무엇이 맞는 리뷰인지 판정할 수 없음

코드는 큰데 테스트가 약함
↓
수정 제안을 실행으로 확인할 수 없음

버그가 너무 오래됨
↓
현재 코드에 다시 넣으면 다른 문제가 됨
```

그래서 대상 프로젝트에는 다음 조건이 필요했어.

1. 실제 사용자가 남긴 버그 이슈가 충분하다.
2. 이슈를 닫은 수정 PR과 커밋을 찾을 수 있다.
3. 자동 테스트로 정답을 검증할 수 있다.
4. 로컬에서 빠르게 실행할 수 있다.
5. 코드가 너무 작지도, 분석이 불가능할 정도로 크지도 않다.
6. 보안 공격을 실제로 수행하지 않고도 재현할 수 있다.

## Flask가 조건에 맞는 이유

### 실제 문제와 수정 이력이 연결돼 있다

이 저장소에 보관한 Flask 자료에는 단순 코드만 있는 게 아니야.

| 자료 | 보관 수 |
|---|---:|
| 전체 이슈 | 2,766개 |
| closed 이슈 | 2,765개 |
| 전체 PR | 2,900개 |
| closed PR | 2,897개 |
| 그중 merged PR | 1,633개 |
| 일반 댓글 | 14,780개 |
| 코드 라인 리뷰 댓글 | 1,304개 |
| 마일스톤 | 38개 |
| 릴리스 | 38개 |
| 공개 보안 권고 | 3개 |

코드만 보면 “이 변경이 왜 필요했는지”를 놓칠 수 있어. 이슈와 댓글까지 같이 보면 사용자가 겪은 증상, 유지보수자의 판단, 실제 수정 방법을 연결할 수 있어.

### 작은 diff 안에 깊은 실행 문제가 있다

Flask 버그는 몇 줄만 바뀌어도 실행 결과가 달라질 수 있어.

예를 들면 이런 종류야.

- 설정값과 명시적 인자의 우선순위
- 요청·앱 컨텍스트의 종료 순서
- URL과 호스트 문자열 해석
- 템플릿 확장자와 자동 이스케이프 판단
- 예외가 여러 정리 작업에 미치는 영향

이런 문제는 문법 검사만으로 잡기 어렵고, 코드가 실제로 어떤 순서로 움직이는지 이해해야 해. AI 리뷰 제품을 비교하기에 좋은 이유야.

### 공개 테스트와 숨은 테스트를 나눌 수 있다

Flask의 기존 `tests/`는 제품도 볼 수 있는 공개 안전망이야.

우리가 만든 `.benchmark-private/tests/`는 제품에게 보여주지 않는 정답 확인 장치야.

```text
공개 테스트 통과
↓
겉으로는 정상처럼 보임
↓
숨은 입력에서만 실패
↓
리뷰 제품이 코드의 의미를 읽어야 발견 가능
```

### 로컬 재현이 가능하다

이 저장소는 Flask 소스와 테스트를 직접 포함해. 외부 유료 API나 운영 서버가 없어도 대부분의 케이스를 재현할 수 있어.

이 점은 같은 실험을 여러 번 반복할 때 중요해. 외부 서비스 상태가 바뀌어서 결과가 흔들리는 일을 줄여주기 때문이야.

## 다른 후보보다 유리한 점

| 기준 | Flask에서 얻는 장점 |
|---|---|
| 언어 | Python이라 실험 코드와 테스트를 읽기 쉽다 |
| 규모 | 저장소 전체 문맥을 요구하지만 운영 불가능할 정도로 크지 않다 |
| 역사 | 오래된 실제 이슈와 최신 이슈가 함께 있다 |
| 검증 | pytest 기반으로 회귀 조건을 실행할 수 있다 |
| 버그 종류 | 문자열, 설정, 컨텍스트, 라우팅, 템플릿 등 종류가 다양하다 |
| 안전성 | 네트워크 공격 없이 로컬 입력으로 재현 가능한 문제가 많다 |

이 표는 다른 프로젝트가 나쁘다는 뜻이 아니야. 이번 첫 실험의 비용과 판정 가능성을 기준으로 Flask가 알맞다는 뜻이야.

## Flask를 쓰는 단점도 있다

좋은 점만 보면 실험이 편향돼.

### Python 중심 결과다

Python의 동적 타입, 예외 처리, 데코레이터 특성이 많이 들어가. 이 결과를 Java, Rust, TypeScript 저장소에 그대로 일반화하면 안 돼.

### 오래된 버그는 현재 코드와 모양이 다르다

원본 patch를 그대로 되돌리는 대신 **버그의 원리**만 현재 코드에 옮겨야 해. 이 과정에서 다른 버그가 섞이지 않았는지 숨은 테스트로 확인해야 한다.

### 저장소 문맥이 비교적 잘 정리돼 있다

Flask는 테스트와 코드 구조가 잘 정리된 편이야. 문서와 테스트가 부족한 사내 저장소에서는 제품 성능이 더 나빠질 수 있다.

### 한 프로젝트만으로 제품 전체를 단정할 수 없다

Flask 파일럿은 가설을 찾는 단계야. 확정 결론을 내리려면 다음 단계에서 다른 언어·다른 규모 프로젝트로 재시험해야 한다.

## 문제를 고르는 깔때기

```text
closed 이슈와 PR 전체
↓
버그로 분류 가능한 항목
↓
수정 또는 회귀 테스트가 있는 항목
↓
현재 코드에 안전하게 이식 가능한 항목
↓
공개 테스트는 통과하고 숨은 테스트만 실패하는 항목
↓
실험 케이스 채택
```

각 후보마다 아래를 기록한다.

| 필드 | 내용 |
|---|---|
| 원본 이슈 | 사용자 증상과 기대 동작 |
| 원본 PR | 실제 수정과 토론 |
| 깨진 불변식 | 항상 지켜져야 하지만 깨진 규칙 |
| 공개 테스트 | 제품이 볼 수 있는 검사 |
| 숨은 테스트 | 제품에게 숨기는 결정적 입력 |
| 안전성 | 외부 피해 없이 실행 가능한지 |
| 이식 난이도 | 현재 코드에 한 가지 문제만 넣을 수 있는지 |
