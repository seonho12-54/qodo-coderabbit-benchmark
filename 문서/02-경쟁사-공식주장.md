# 02. 경쟁사 공식 주장

이 문서는 **Qodo와 CodeRabbit이 스스로 잘한다고 말하는 항목을 실제 시험 질문으로 바꾸는 곳**이야.

기준일: 2026-09-03

중요한 구분이 있어.

> 아래 내용은 경쟁사의 공식 주장이지, 우리가 확인한 결과가 아니야.

## 왜 공식 주장을 먼저 적나

결과를 먼저 본 뒤 비교 항목을 고르면 유리한 제품에 맞춰 기준이 흔들릴 수 있어.

그래서 순서를 바꿔.

```text
경쟁사가 공식적으로 주장한 능력 수집
↓
주장을 검증 가능한 질문으로 변환
↓
질문에 맞는 Flask 케이스 배치
↓
실제 결과로 확인
```

## Qodo가 공식적으로 말하는 것

Qodo의 현재 Code Review 문서는 Qodo 2의 경험을 설명해. 공식 문서에서 강조하는 내용은 다음과 같아.

| 공식 주장 | 쉬운 뜻 | 이번 실험의 확인 질문 |
|---|---|---|
| 여러 전문 리뷰 에이전트가 PR을 분석 | 한 번의 일반 리뷰가 아니라 역할별 관점으로 본다는 뜻 | 서로 다른 종류의 버그를 고르게 찾는가? |
| 전체 저장소 문맥과 PR 이력을 사용 | 바뀐 줄만 보지 않고 주변 코드와 과거 결정을 참고한다는 뜻 | 변경 줄 밖의 호출 순서·설정 의미까지 연결하는가? |
| 높은 recall과 precision, 낮은 noise | 실제 문제는 많이 잡고 틀린 경고는 적게 남긴다는 뜻 | 결함 탐지율과 정상 PR 오탐률이 동시에 좋은가? |
| 중요한 문제를 우선 표시 | 사소한 스타일보다 장애 가능성이 큰 문제를 먼저 보여준다는 뜻 | 실제 버그가 낮은 중요도로 묻히지 않는가? |
| 원인과 조치 방향을 설명 | 경고만 하지 않고 왜 문제인지와 다음 행동을 알려준다는 뜻 | 원인·발생 조건·결과와 실행 가능한 수정이 있는가? |
| 조직 규칙을 문맥에 맞게 적용 | 저장소 규칙을 모든 PR에 일관되게 적용한다는 뜻 | 동일 규칙의 변형 케이스에서 판정이 안정적인가? |

## CodeRabbit이 공식적으로 말하는 것

CodeRabbit의 PR Review 문서는 자동·증분 리뷰와 저장소 문맥 기반 피드백을 강조해.

| 공식 주장 | 쉬운 뜻 | 이번 실험의 확인 질문 |
|---|---|---|
| 런타임 오류, race condition, 논리 오류 탐지 | 실행했을 때 깨지는 다양한 문제를 찾는다는 뜻 | 숨은 테스트로만 드러나는 실제 실행 오류를 찾는가? |
| 전체 코드베이스 기반 제안 | 변경 줄 주변뿐 아니라 저장소 관계를 본다는 뜻 | 호출자·설정·다른 파일의 규칙까지 연결하는가? |
| 여러 AI 모델과 정적 분석 도구 사용 | AI 추론과 기존 검사기를 함께 쓴다는 뜻 | 문법 검사 밖의 의미 버그와 정적 검사 문제를 구분하는가? |
| 40개 이상의 linter·보안 scanner 연동 | 알려진 규칙 기반 검사 범위가 넓다는 뜻 | 도구 경고를 반복할 뿐인지, Flask 고유 원인을 찾는지 구분되는가? |
| 한 번 클릭하는 수정 제안 | 댓글에서 바로 변경을 적용할 수 있다는 뜻 | 적용한 수정이 숨은 테스트와 전체 테스트를 통과하는가? |
| 새 commit만 보는 증분 리뷰 | 이미 본 내용을 반복하지 않고 새 변경에 집중한다는 뜻 | 두 번째 commit에서 새 문제를 찾고 해결된 댓글을 반복하지 않는가? |
| 피드백을 기억하는 Learnings | 팀이 알려준 선호와 규칙을 다음 리뷰에 반영한다는 뜻 | 같은 규칙을 다른 형태로 보여줬을 때 일관되게 적용하는가? |
| 연결된 이슈의 요구사항 검증 | PR이 이슈의 목적을 충족하는지 확인한다는 뜻 | 요구사항을 준 라운드에서 기능 누락을 정확히 찾는가? |

공식 출처:

- [CodeRabbit 코드 리뷰 개요](https://docs.coderabbit.ai/guides/code-review-overview)
- [CodeRabbit 플랫폼 개요](https://docs.coderabbit.ai/index)

## 두 제품의 공통 주장

둘 다 다음 영역을 강조해.

```text
저장소 문맥 이해
+
실제 버그 탐지
+
잡음 감소
+
수정 가능한 피드백
+
팀 규칙 반영
```

기능표에서는 비슷해 보여도 실험에서는 각각 따로 쪼개서 봐야 해.

예를 들어 “문맥을 본다”는 말은 너무 넓어. 이번 실험에서는 이렇게 나눈다.

- 같은 파일 안의 앞뒤 코드 연결
- 다른 파일의 호출자 연결
- 설정값과 명시적 인자의 우선순위 연결
- 실행 순서와 예외 전파 연결
- 과거 PR·이슈와 현재 변경 연결
- 티켓 요구사항과 실제 diff 연결

## 주장별 실험 연결표

| 검증 축 | 우선 사용할 표본 | 확인 증거 |
|---|---|---|
| 문자열·입력 경계 | P01 계열 | 특정 입력, 파싱 결과, 실행 인자 |
| 생명주기·실행 순서 | P02 계열 | callback 실행 순서와 예외 |
| 설정 우선순위 | P03 계열 | 명시값과 기본값 충돌 결과 |
| 파일명·대소문자 경계 | P04 계열 | 여러 확장자 입력 결과 |
| 정상 변경의 잡음 | C01, C02 | 성립하지 않는 경고 수 |
| 수정 제안 품질 | 정확·부분 탐지 댓글 | 숨은 테스트와 전체 테스트 결과 |
| 반복 안정성 | 후속 변형 케이스 | 같은 불변식을 다시 찾는 비율 |

## 실행 때 반드시 기록할 제품 정보

제품 이름만 적으면 나중에 같은 조건을 재현할 수 없어.

```text
제품:
실행 날짜와 UTC 시각:
제품 버전 또는 화면에 표시된 릴리스:
요금제:
GitHub App 권한:
자동 리뷰 여부:
draft PR 리뷰 여부:
설정 파일 경로와 SHA:
추가 지시 원문:
연결한 외부 도구:
재실행 횟수와 이유:
```

## 판정 전에 하지 않을 말

- “Qodo가 더 똑똑하다”
- “CodeRabbit이 더 정확하다”
- “댓글이 많으니 더 많이 잡았다”
- “공식 페이지에 적혀 있으니 실제로도 된다”

이 문서의 역할은 승자를 고르는 게 아니야. 각 주장을 시험 가능한 질문으로 고정하는 거야.

딱 기억해.

**공식 주장은 출발점이고, Flask PR에서 나온 재현 가능한 증거가 결론이야.**
