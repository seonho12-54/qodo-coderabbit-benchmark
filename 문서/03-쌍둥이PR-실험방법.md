# 03. 쌍둥이 PR 실험 방법 — 두 제품이 똑같은 코드를 봤다고 증명하려고

## 쌍둥이 PR이란

하나의 변경 커밋으로 현재 저장소에 만든 PR 두 개야.

```text
같은 시작 코드
↓
같은 변경 커밋 한 개
├── 첫 PR → Qodo 명령만 실행
└── 둘째 PR → CodeRabbit 명령만 실행
```

PR 번호와 브랜치 이름만 다르고, 제품이 보는 변경 내용은 같아야 해.

## 실행 저장소

| 저장소 | PR | 실행할 제품 |
|---|---|---|
| 현재 저장소 | 첫 쌍둥이 PR | Qodo만 |
| 현재 저장소 | 둘째 쌍둥이 PR | CodeRabbit만 |

이 표로 두 제품이 서로의 리뷰 댓글을 보는 일을 막을 수 있어.

저장소 이름에는 `qodo`, `coderabbit`, `benchmark`, `test`, `bug`, `defect`, `oracle`, `P01` 같은 단어를 넣지 않는다.

## 쌍둥이 PR에 넣을 것

- 실행에 필요한 Flask 코드
- 설치 파일과 잠금 파일
- 두 제품에 똑같이 보여줄 공개 테스트
- 중립적인 작업 설명

## 쌍둥이 PR에 새로 넣지 않을 것

- `benchmark/`
- `.benchmark-private/`
- `benchmark/oracles/`
- 이 저장소의 한국어 실험 문서
- `CHANGES.rst`, `docs/changes.rst`
- 원본 이슈와 수정 PR 주소
- 문제 번호와 정답 설명
- Qodo와 CodeRabbit을 함께 부르는 설정

## PR 하나를 만드는 순서

1. 두 PR의 시작 코드가 같은지 확인한다.
2. 중립적인 작업 브랜치에서 실제 개발 변경을 만든다.
3. 찾아야 할 버그는 하나만 넣는다.
4. 공개 테스트는 정상 개발자가 넣을 만한 범위만 넣는다.
5. 커밋 하나를 두 작업 브랜치에 그대로 보낸다.
6. 제목과 설명이 같은 PR 두 개를 연다.
7. 두 PR의 변경 내용이 같은지 확인한다.
8. 정해 둔 순서대로 두 제품의 리뷰를 요청한다.

## 같다는 것을 확인할 값

| 값 | 같아야 하는 이유 |
|---|---|
| 시작 코드 번호 | 출발점이 같아야 함 |
| 변경 코드 번호 | 같은 커밋인지 확인 |
| 바뀐 파일 목록 | 한쪽만 더 본 파일이 없어야 함 |
| 추가·삭제 줄 수 | 변경 크기가 같아야 함 |
| 변경 내용 지문 | 실제 코드가 한 글자까지 같은지 확인 |
| PR 제목과 설명 | 한쪽에만 힌트를 주지 않아야 함 |

이 표의 값이 하나라도 다르면 그 PR 쌍은 실행하지 않거나 점수에서 뺀다.

## 제품을 나누는 방법

두 제품의 자동 리뷰는 끄고 PR마다 필요한 제품 명령만 보낸다. 같은 저장소에서 실행하므로 완전한 분리가 아니라는 한계를 결과에 기록한다.

## 실행 순서

- 홀수 문제: Qodo 요청 후 CodeRabbit 요청
- 짝수 문제: CodeRabbit 요청 후 Qodo 요청
- 두 리뷰가 끝날 때까지 사람 댓글 금지
- 리뷰가 끝난 즉시 각 저장소의 원본 JSON 저장
- 저장이 끝난 뒤에만 정답을 열고 판정

## 바로 멈춰야 할 때

- 두 PR의 변경 내용 지문이 다름
- 한쪽에만 추가 커밋이 생김
- 한 제품이 상대 제품의 댓글을 볼 수 있음
- 제품 권한이나 공개 테스트가 서로 다름

딱 기억해.

**쌍둥이 PR은 비슷한 PR 두 개가 아니라, 같은 커밋을 두 제품에게 따로 보여주는 시험이야.**
