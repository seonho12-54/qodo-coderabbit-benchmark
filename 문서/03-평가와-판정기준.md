# 03. 평가와 판정 기준

이 문서는 **리뷰 댓글이 실제 버그를 잡았는지 같은 기준으로 판정하는 정답표**야.

## 왜 기준을 먼저 정하나

리뷰 댓글은 그럴듯하게 들릴 수 있어.

예를 들어 이런 댓글이 있다고 해.

> 엣지 케이스를 확인하고 테스트를 추가하세요.

말은 맞아 보이지만 어떤 입력에서 무엇이 깨지는지 없어. 이런 댓글까지 정답으로 세면 댓글을 많이 쓰는 제품이 유리해져.

그래서 결과를 보기 전에 판정 규칙을 고정한다.

## 판정 단위

세 단계로 나눠서 본다.

```text
댓글 하나
= finding 단위

PR 하나
= case 단위

같은 설정으로 수행한 전체 PR 묶음
= run 단위
```

한 댓글이 길어도 같은 원인에 대한 설명이면 finding 하나야. 같은 문제를 요약 댓글과 인라인 댓글에서 반복하면 중복 finding으로 묶는다.

## 정확히 탐지의 세 조건

댓글에 다음 세 가지가 모두 있어야 `정확히 탐지`야.

| 요소 | 질문 |
|---|---|
| 원인 | 코드의 어떤 판단이나 순서가 잘못됐는가? |
| 발생 조건 | 어떤 입력·설정·호출 순서에서 문제가 생기는가? |
| 결과 | 사용자나 시스템에 어떤 잘못된 동작이 나타나는가? |

정확한 줄 번호가 없어도 세 요소를 코드 위치와 연결하면 인정할 수 있어. 반대로 줄 번호만 맞고 문제 설명이 틀리면 인정하지 않는다.

## 네 가지 핵심 판정

| 판정 | 뜻 | 예시 형태 |
|---|---|---|
| 정확히 탐지 | 원인·발생 조건·결과가 모두 맞음 | “명시값이 기본값 분기 안에서만 처리돼 특정 설정에서 OPTIONS가 빠진다” |
| 부분 탐지 | 핵심 방향은 맞지만 세 요소 중 하나 이상이 빠짐 | “이 조건문 위치 때문에 OPTIONS 처리에 문제가 있을 수 있다” |
| 놓침 | 실제 결함을 언급하지 않음 | 관련 댓글 없음 |
| 오탐 | 정상 코드에 성립하지 않는 문제를 주장 | 정상 리팩터링을 동작 변경이라고 경고 |

추가 표시는 다음과 같아.

| 표시 | 뜻 |
|---|---|
| 중복 | 이미 나온 같은 원인을 다시 말함 |
| 잡음 | 스타일·취향 위주라 결함 판단에 도움이 안 됨 |
| 근거 오류 | 존재하지 않는 API 동작이나 코드 흐름을 근거로 듦 |
| 범위 밖 | 이번 PR과 관계없는 기존 문제를 지적함 |

## 부분 탐지 세부 점수

판정자가 왜 부분 탐지로 봤는지 남기기 위한 보조 점수야.

| 항목 | 0점 | 1점 |
|---|---|---|
| 코드 위치 | 위치가 틀리거나 없음 | 문제 위치 또는 직접 원인을 짚음 |
| 원인 | 틀림 | 맞음 |
| 발생 조건 | 없음·틀림 | 맞음 |
| 결과 | 없음·틀림 | 맞음 |

- 4점: 정확히 탐지 후보
- 2~3점: 부분 탐지 후보
- 0~1점: 놓침 또는 관련 없는 댓글

최종 판정은 숨은 테스트와 원본 수정 이력으로 확인한다. 점수만으로 자동 확정하지 않는다.

## 수정 제안 판정

댓글이 문제를 잘 설명해도 수정 코드가 틀릴 수 있어.

수정 제안은 별도로 확인한다.

```text
제안 patch를 별도 브랜치에 적용
↓
숨은 회귀 테스트 실행
↓
Flask 전체 공개 테스트 실행
↓
새로운 실패가 생겼는지 확인
```

| 판정 | 조건 |
|---|---|
| 수정 성공 | 숨은 테스트와 전체 공개 테스트 모두 통과 |
| 부분 수정 | 원래 증상 일부만 해결하거나 입력 일부만 통과 |
| 수정 실패 | 숨은 테스트 실패 또는 새 회귀 발생 |
| 실행 불가 | patch가 적용되지 않거나 코드가 실행되지 않음 |
| 제안 없음 | 설명만 있고 적용 가능한 변경이 없음 |

제품이 여러 수정안을 내면 최초 제안과 최종 제안을 모두 기록한다. 나중에 나온 가장 좋은 답만 골라 제품 성공으로 세지 않는다.

## 정상 대조군 판정

정상 PR은 버그가 없는 시험지야.

다음은 오탐이야.

- 실제로 발생하지 않는 런타임 오류 주장
- 동일한 동작을 바꿨다고 잘못 판단
- Flask나 Python API 의미를 틀리게 설명
- 필요하지 않은 방어 코드가 없어서 위험하다고 단정

다음은 오탐으로 세지 않지만 잡음으로 기록해.

- 이름을 더 읽기 쉽게 바꾸자는 취향 제안
- 문서나 주석을 더 쓰자는 일반 제안
- 성능 근거가 없는 미세 최적화

## 시간 측정

시간은 세 개만 기록한다.

| 시간 | 시작과 끝 |
|---|---|
| 첫 반응 시간 | 리뷰 요청 → 제품의 첫 댓글 |
| 첫 정답 시간 | 리뷰 요청 → 첫 정확·부분 탐지 댓글 |
| 완료 시간 | 리뷰 요청 → 제품이 리뷰 완료를 표시한 시각 |

제품이 댓글을 빨리 남겼어도 정답이 아니면 `첫 정답 시간`은 기록되지 않는다.

## 핵심 지표 계산

### 정확 탐지율

```text
정확히 탐지한 결함 케이스 수 / 전체 결함 케이스 수
```

### 의미 있는 탐지율

```text
(정확히 탐지 + 부분 탐지 케이스 수) / 전체 결함 케이스 수
```

### 정상 PR 오탐률

```text
오탐이 하나 이상 나온 정상 케이스 수 / 전체 정상 케이스 수
```

### 엄격한 댓글 정밀도

```text
정확한 finding 수 / (정확한 finding 수 + 오탐 finding 수)
```

### 근본 원인 적중률

```text
원인을 정확히 설명한 결함 케이스 수 / 전체 결함 케이스 수
```

### 수정 성공률

```text
테스트를 모두 통과한 최초 수정 제안 수 / 실행 가능한 최초 수정 제안 수
```

### 반복 안정성

```text
같은 불변식의 변형을 정확히 탐지한 수 / 해당 변형 전체 수
```

## 블라인드 판정 절차

```text
수집 담당자가 댓글 원문 저장
↓
제품 이름·아이콘·말투 단서 제거
↓
판정자 1과 판정자 2가 독립 채점
↓
불일치 항목만 근거 비교
↓
숨은 테스트 실행 결과로 최종 결정
```

판정 기록에는 감상 대신 근거를 남긴다.

```text
case_id:
finding_id:
blind_product_id:
verdict:
cause_evidence:
trigger_evidence:
impact_evidence:
code_location:
hidden_test_result:
adjudicator_1:
adjudicator_2:
final_reason:
```

## 동점일 때 보는 순서

종합 점수 하나로 중요한 차이를 숨기지 않는다.

우선순위는 다음과 같아.

1. 정확 탐지율
2. 정상 PR 오탐률
3. 근본 원인 적중률
4. 수정 성공률
5. 첫 정답 시간
6. 댓글 수와 편의 기능

## 파일럿 결과의 한계

결함 4개와 정상 2개는 방향을 찾는 표본이야. 이 숫자만으로 모든 코드 리뷰 상황의 승자를 확정하지 않는다.

파일럿의 역할:

- 판정표가 실제로 쓸 수 있는지 확인
- 제품 설치와 결과 수집 흐름 확인
- 반복되는 공통 실패 가설 찾기
- 본 실험에 필요한 케이스 수 계산

딱 기억해.

**정확한 리뷰는 “조심하세요”가 아니라, 어디서 왜 어떤 조건에 깨지고 무슨 결과가 생기는지를 맞히는 리뷰야.**
