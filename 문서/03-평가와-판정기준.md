# 03. 결과를 판단하는 기준

> 이 문서는 예비시험 판정 기록이야. 본시험은 [새 판정 기준](05-평가와-판정기준.md)을 사용해.

이 문서는 **제품 댓글을 보고 “찾음, 일부만 찾음, 못 찾음, 잘못된 경고” 중 무엇인지 정하는 규칙**이야.

## 왜 규칙을 먼저 정했나

제품 결과를 먼저 본 뒤 규칙을 만들면 원하는 제품에 유리하게 점수를 줄 수 있어.

그래서 리뷰를 시작하기 전에 다음을 미리 정했어.

- 각 PR에서 찾아야 하는 핵심 버그
- 버그가 생기는 입력이나 실행 순서
- 사용자에게 생기는 문제
- 제품에 안 보여줄 정답 테스트
- 어떤 댓글을 정답으로 인정할지

## “제대로 찾음”의 기준

제품 댓글에 아래 세 가지가 모두 있어야 해.

```text
원인
+= 코드의 어떤 판단이 잘못됐는가
+
+조건
+= 어떤 입력이나 실행 순서에서 문제가 생기는가
+
+결과
+= 사용자가 어떤 오류나 잘못된 동작을 겪는가
```

예를 들어 이런 말은 부족해.

> 예외 상황을 확인하고 테스트를 추가하세요.

어떤 입력에서 무엇이 왜 깨지는지 말하지 않았기 때문이야.

## 네 가지 결과

| 결과 | 쉬운 뜻 | 예시 |
|---|---|---|
| 제대로 찾음 | 원인·조건·결과를 모두 맞힘 | IPv6 주소를 잘못 잘라 서버가 시작되지 않는다고 설명 |
| 일부만 찾음 | 문제 방향은 맞지만 중요한 설명이 빠짐 | 주소 처리 문제라고만 말하고 어떤 주소인지 설명하지 않음 |
| 못 찾음 | 실제 버그를 말하지 않음 | 관련 댓글이 없음 |
| 잘못된 경고 | 정상 코드를 버그라고 말함 | 동작이 같은 코드 정리를 오류라고 말함 |

## 댓글 개수는 점수가 아니다

같은 문제를 요약과 코드 줄에 두 번 적어도 문제 하나를 찾은 것으로 계산해.

반대로 댓글을 열 개 남겨도 실제 버그와 관계없는 말뿐이면 점수가 올라가지 않아.

## 수정 코드는 따로 확인한다

문제를 찾는 것과 제대로 고치는 것은 다른 일이야.

```text
제품이 코드 수정안 제공
↓
우리가 별도 코드에 적용
↓
그 버그를 확인하는 정답 테스트 실행
↓
기존 테스트 전체 실행
↓
결과 결정
```

| 결과 | 뜻 |
|---|---|
| 완전히 고침 | 정답 테스트와 기존 테스트가 모두 통과하고 다른 고장이 없음 |
| 일부만 고침 | 처음 문제는 고쳤지만 다른 문제가 남음 |
| 못 고침 | 정답 테스트가 계속 실패하거나 새 문제가 생김 |
| 적용할 수 없음 | 제품이 실제 코드를 주지 않았거나 코드가 들어가지 않음 |

## 테스트 실패를 읽는 방법

버그를 넣은 P01~P04에서는 정답 테스트가 실패해야 해.

```text
버그를 넣은 코드에서 정답 테스트 실패
+= 버그가 실제로 나타남
```

```text
정상 코드에서 정답 테스트 통과
+= 버그가 없음
```

이 테스트 결과는 **코드에 버그가 있는지** 보여줘.

제품이 그 버그를 찾았는지는 **제품 댓글 내용**으로 따로 판단해.

## 정상 코드 시험

C01과 C02에는 버그가 없어.

제품이 여기에 없는 문제를 만들어 내면 “잘못된 경고”로 기록해.

스타일 제안이나 문서 작성 팁처럼 버그와 상관없는 말은 잘못된 경고 점수에는 넣지 않지만, 읽는 사람을 피곤하게 만드는 불필요한 말로 따로 기록해.

## 비교하는 숫자

| 숫자 | 무엇을 뜻하나 |
|---|---|
| 버그를 제대로 찾은 비율 | 버그 시험 중 원인·조건·결과를 모두 맞힌 비율 |
| 정상 코드에 잘못 경고한 비율 | 정상 시험 중 없는 문제를 만들었다고 말한 비율 |
| 진짜 원인까지 맞힌 비율 | 겉으로 보이는 현상 말고 코드의 잘못된 판단을 맞힌 비율 |
| 수정 코드 성공 비율 | 제품이 준 수정 코드가 실제 테스트를 모두 통과한 비율 |
| 처음 제대로 찾기까지 걸린 시간 | 리뷰를 요청한 뒤 첫 정답 댓글까지 걸린 시간 |
| 반복해서 다시 찾는 비율 | 같은 버그를 다른 코드 모양에서도 다시 찾은 비율 |

시간은 평균 대신 가운데 값을 사용했어.

예를 들어 61초, 70초, 88초라면 가운데 있는 70초를 쓰는 거야. 한 번 유난히 느린 실행 때문에 전체 결과가 크게 흔들리지 않게 하기 위해서야.

## P02와 P04 처리

P02와 P04에는 원래 생각한 것과 달리 서로 다른 문제가 두 개씩 생겼어.

결과를 본 뒤 정답을 바꾸지는 않았어.

대신 두 결과를 나눠 적었어.

```text
처음부터 찾으라고 정한 핵심 버그
+= 원래 점수에 사용
+
+리뷰 중 새로 발견한 다른 버그
+= 맞는 발견이라고 기록하지만 원래 점수에는 넣지 않음
```

또 한 PR에 버그 하나만 넣는 규칙을 지킨 P01과 P03의 결과도 따로 봤어. 다만 두 개뿐이라 최종 결론을 내리기에는 부족해.

## 이번 시험의 한계

- 버그 시험 4개와 정상 시험 2개뿐이야.
- Python과 Flask만 사용했어.
- 다른 사람이 제품 이름을 가리고 다시 채점하지 않았어.
- 같은 버그를 다른 코드 모양으로 반복하지 않았어.

딱 기억해.

**코드가 고장났는지는 정답 테스트로 확인하고, 제품이 그 고장을 알아냈는지는 댓글의 원인·조건·결과로 판단해.**
