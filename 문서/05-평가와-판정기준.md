# 05. 평가와 판정 기준 — 두 제품의 말을 같은 자로 재려고

## 먼저 제품 이름을 가린다

판정하는 사람은 댓글이 Qodo 것인지 CodeRabbit 것인지 모르는 상태에서 읽는다. 제품 이름 대신 A와 B만 쓴다.

## 버그를 찾았다고 인정하는 조건

다음 네 가지가 모두 맞아야 **정확히 찾음**이야.

1. 문제가 있는 위치나 실행 흐름
2. 코드가 잘못되는 이유
3. 문제가 생기는 입력이나 순서
4. 사용자에게 생기는 잘못된 결과

“엣지 케이스를 확인하세요”나 “테스트를 더 넣으세요”처럼 어디서 무엇이 깨지는지 말하지 않은 댓글은 정답으로 세지 않는다.

## 판정 이름

| 판정 | 쉬운 뜻 |
|---|---|
| 정확히 찾음 | 위치·원인·조건·결과를 모두 맞힘 |
| 일부 찾음 | 방향은 맞지만 중요한 설명이 빠짐 |
| 못 찾음 | 주 문제를 말하지 않음 |
| 잘못된 경고 | 정상 코드에 없는 문제를 있다고 말함 |
| 스타일 의견 | 이름이나 표현에 관한 취향이며 버그 점수와 분리 |

이 표로 말이 그럴듯하다는 이유만으로 정답 점수를 주는 일을 막을 수 있어.

같은 문제를 여러 댓글에서 반복해도 한 건으로 센다. 댓글 개수는 실력 점수가 아니야.

## 수정 코드 확인

제품이 실제 코드에 적용할 수 있는 수정안을 줬을 때만 다음을 확인한다.

1. 별도 작업 공간에 제품의 수정 코드를 그대로 적용
2. 충돌 없이 적용되는지 확인
3. 공개 테스트 실행
4. 제품에 안 보여준 정답 테스트 실행
5. 원래 되던 기능이 새로 깨지지 않았는지 확인

| 수정 결과 | 뜻 |
|---|---|
| 완전히 고침 | 공개 테스트와 정답 테스트 모두 통과 |
| 일부만 고침 | 정답 테스트 일부만 통과 |
| 적용 실패 | 제품이 준 코드가 들어가지 않음 |
| 다른 기능을 깨뜨림 | 원래 통과하던 테스트가 실패 |
| 수정 코드 없음 | 설명만 있고 적용할 코드는 없음 |

이 표로 “고칠 수 있을 것 같다”와 “실제로 고쳤다”를 구분할 수 있어.

사람이 제품 설명을 보고 대신 코드를 작성하면 제품의 수정 능력을 잰 것이 아니므로 금지한다.

## 판정 기록에 반드시 남길 것

- 가린 제품 이름
- 사례 이름
- 판정
- 근거가 되는 제품 댓글
- 정답의 네 항목과 비교한 내용
- 수정 코드가 있다면 적용 결과
- 판정한 사람과 다시 확인한 사람
- 의견이 갈렸다면 최종 이유

딱 기억해.

**버그 위치만 비슷하게 말한 것은 정답이 아니고, 왜·언제·무슨 일이 생기는지까지 맞혀야 해.**
